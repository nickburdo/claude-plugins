## Решения пользователя

- **Разбиение на PR:** 4 PR по очереди — #5, #1, #2+#3, #4.
- **#1 (коммиты):** поле конфига `commitMode: manual | per-step | at-end`, по умолчанию `manual`; если инструкции проекта (например, `CLAUDE.md`) противоречат полю — скилл спрашивает пользователя; push и создание PR скиллы не делают ни в каком режиме.
- **#2 (проверки, падающие на основной ветке):** вариант C — эвристика + вопрос, без изменения конфига: если ни один упавший файл не изменён на ветке, падение помечается «вероятно существовало до задачи», скилл спрашивает, продолжать ли, и предлагает его в бэклог.
- **#3 (старые замечания ревью):** отдельный список «Pre-existing», верифицированный так же, как находки (место, сценарий сбоя).
- **#4 (объём browser check):** если объём в плане не указан (старые планы, ручной вызов агента) — `full`, как сейчас.
- **План:** один файл на все PR; лежит в ветке PR 1.
- **Версии:** поднимать в каждом PR: 0.1.1 → 0.2.0 → 0.3.0 → 0.4.0.
- **Ветки:** `fix/start-task-ff-only-pull`, `feat/commit-mode`, `feat/pre-existing-issues`, `feat/browser-check-scope` — каждая от актуального `main` после мержа предыдущего PR.

## Открытые предложения (одобряются вместе с планом)

1. **`commitMode` — семантика:**
   - `manual` — скиллы не коммитят; finish-task останавливается перед коммитом (как сейчас).
   - `per-step` — после каждой выполненной задачи плана один коммит; исправления по ревью в finish-task — отдельным коммитом; отметки в плане / done-log / роадмапе — финальным коммитом.
   - `at-end` — во время задач не коммитить; finish-task после отчёта и подтверждения пользователя делает один коммит.
   - Сообщение коммита: по правилам проекта, если они есть; иначе `<type>: <кратко>` по типу ветки.
   - Без поля в конфиге — `manual`.
2. **`commitMode` и code review:** в промпт ревью из finish-task добавить, что коммиты на ветке ожидаемы по `commitMode` и не являются находкой.
3. **#2 — правила эвристики:**
   - упавшие файлы берутся из вывода команды и сравниваются с `git diff --name-only <mainBranch>...HEAD` плюс незакоммиченные изменения;
   - хотя бы один упавший файл изменён на ветке → падение новое, остановка как сейчас (консервативно, даже если в файле есть и старые ошибки);
   - файлы из вывода определить нельзя → показать вывод и спросить пользователя (новое → стоп / существовало до задачи → продолжить);
   - падение, которое пользователь признал существовавшим, идёт в шаг 3 кандидатом в бэклог вместе со списком «Pre-existing» из #3.
4. **#4 — формат объёма в плане:** пункт browser check в финальной задаче плана (и в чат-плане chore) пишется как `Browser check — объём: full | short (сценарии: …) | none (причина: …)`.
   - Вопрос об объёме задаётся в шаге 2 start-task (в том же `AskUserQuestion`, что и имя ветки), только если задача, вероятно, затронет `config.uiPaths`.
   - `short` — только перечисленные сценарии плюс ошибки консоли; ширины и темы — только если названы в сценарии.
   - `none` — finish-task пропускает browser check и пишет причину в отчёт.
   - Повторный browser check после исправлений по ревью — с тем же объёмом.
5. **#4 — действия, меняющие данные:** browser-checker не выполняет удаление, импорт, сброс и другие действия, меняющие данные, если сценарий плана явно этого не требует; если требует — в начале отчёта предупреждает, какие данные изменятся. Пропущенные из-за этого проверки — в списке «Not done».
